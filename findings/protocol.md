- **A RETRY THAT NEVER EXHAUSTS IS WORSE THAN A WRONG VERDICT — FIXED 2026-09-22.** `handle_red()` read the attempt count from the step record *after* `mark()` had replaced that record wholesale, so `tries` was always 0, the budget never ran out and `on_fail.exhausted` was unreachable. Measured on live campaign `rel2-b38a0d1-20260921T214403Z`: `s1-download` executed 7 times in 3 minutes against `retries: 2`, `state.json` stuck at `tries: 1`, and the campaign could not reach ANY verdict — it would have spun all night. Three changes: the count is read before `mark()` and carried through it; `advance()` now counts executions itself and halts with `RUNNER-ERROR` / INVALID-INSTRUMENT above `retries+1`, so an accounting regression is LOUD instead of silent; and `s1-download` is now idempotent (`rm -rf {MATRIX_WORK}/dl &&` before `gh run download`), because `gh` refuses to overwrite an existing file and a half-extracted tree makes every retry fail with `file exists` forever. **A command under RETRY must be idempotent or the retry policy is a lie.** Armed by `protocol/scenarios/defect-retry-exhausts`, which grades the attempt COUNT and the halt VERDICT — the defect re-introduced is caught on both (`INVALID-INSTRUMENT` / `RUNNER-ERROR: step attempted 4 times`), the fix passes clean.
