- QREXEC CAN GO MISSING FOR GOOD AFTER A CLEAN INSTALL, and the permanence is a service-configuration defect of ours. Measured 2026-09-06 twice (win11-supp, win11-fresh): the guest is Running, Windows fully booted (the PV console served a `login:` prompt and a shell), yet qrexec never answers - so qtest, the gui-agent log and the event log are ALL unreachable, because every one of them rides qrexec. A plain restart cured it in 25 s, so nothing was corrupt: the service simply had not started on that boot. WHY IT STAYED DEAD is in the configuration the MSI leaves: `QrexecAgent` = AUTO_START, ERROR_CONTROL **IGNORE**, DEPENDENCIES **QdbDaemon**, and `sc qfailure` empty (RESET_PERIOD 0) - no recovery actions, so one failed start is final and silent. FIX (installer, d803be8, `Set-QubesServiceRecovery`): arm Windows recovery on QdbDaemon+QrexecAgent (restart 5 s/15 s/60 s, reset daily) AND `sc failureflag 1`, which is what makes the actions apply to a service that EXITS WITH AN ERROR rather than only one that crashes. Verified installed on every primed guest (`RESET_PERIOD 86400`, `RESTART 5000/15000/60000`). **THE TRIGGER IS STILL UNIDENTIFIED**: 13 natural install cycles since the fix produced ZERO recurrences and NO SCM 7000/7001/7009 for either Qubes service (only benign luafv / Sync Host). Absence of recurrence is not identification, and failure actions may not even apply to a dependency-failed start (SCM 1068 never launches the process) - so the fix is RESILIENCE, not a proven root-cause cure. Leading candidate remains QdbDaemon losing the race on the one boot where the PV drivers were just installed. Next occurrence: PRESERVE the guest and interrogate it over the console; never restart it (two failure states were destroyed that way). [verified 2026-09-06]
