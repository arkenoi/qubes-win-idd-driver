- P2 [FIXED AND PROVEN 2026-09-09] THE STAGE-1 REBOOT WAS A COIN FLIP; IT IS NOW A DEFINED PATH. A pristine guest has no PV drivers bound, so stage 1's reboot went out via the emulated ACPI/CF9 reset. In QEMU that raises `qemu_system_reset_request`, and TWO consumers race for it: the generic main loop (`qemu_system_reset` -> `qemu_devices_reset`, an IN-PLACE reset that never tells Xen) and the Xen accelerator's ioreq handler (`destroy_hvm_domain` -> SHUTDOWN_reboot -> toolstack -> on_reboot=destroy). Domain-destroys is the INTENDED Qubes behaviour; the in-place reset is the leak. FIX (guest-side, stands alone): stage 1 requests an ACPI S5 POWEROFF, which sets `shutdown_requested` - a separate flag with no `qemu_system_reset` path, whose only consumer is the Xen ioreq handler - so the domain goes down every time and the next start is always a fresh domain with the PV bus bound. It costs no capability: under Qubes a guest cannot restart itself either way (on_reboot=destroy), so `/r` never bought a self-restart, only a chance of an invisible in-place reset. Fast Startup is SET AND VERIFIED in the same block, because `shutdown /s` with hiberboot enabled is a hybrid shutdown whose next start RESUMES instead of booting - that would defeat the fix silently, and client Windows ships with it ON.
