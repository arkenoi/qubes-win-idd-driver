- P2 [FIXED AND PROVEN 2026-09-09] THE STAGE-1 REBOOT WAS A COIN FLIP; IT IS NOW A DEFINED PATH. A pristine guest has no PV drivers bound, so stage 1's reboot went out via the emulated ACPI/CF9 reset. In QEMU that raises `qemu_system_reset_request`, and TWO consumers race for it: the generic main loop (`qemu_system_reset` -> `qemu_devices_reset`, an IN-PLACE reset that never tells Xen) and the Xen accelerator's ioreq handler (`destroy_hvm_domain` -> SHUTDOWN_reboot -> toolstack -> on_reboot=destroy). Domain-destroys is the INTENDED Qubes behaviour; the in-place reset is the leak. FIX (guest-side, stands alone): stage 1 requests an ACPI S5 POWEROFF, which sets `shutdown_requested` - a separate flag with no `qemu_system_reset` path, whose only consumer is the Xen ioreq handler - so the domain goes down every time and the next start is always a fresh domain with the PV bus bound. It costs no capability: under Qubes a guest cannot restart itself either way (on_reboot=destroy), so `/r` never bought a self-restart, only a chance of an invisible in-place reset. Fast Startup is SET AND VERIFIED in the same block, because `shutdown /s` with hiberboot enabled is a hybrid shutdown whose next start RESUMES instead of booting - that would defeat the fix silently, and client Windows ships with it ON. EVIDENCE: 7 clean installs on the fixed path, 7/7 DESTROY, 0 WARM, 0 UNKNOWN, confirmed by a second instrument. CAVEAT ON STRENGTH, because the raw numbers overstate it: the historical control ("8 destroy / 6 warm" over 14 runs) was measured with prime-run's `restarts` counter alone, a 20 s poll that demonstrably misses short halts - three of the seven fixed-path runs recorded restarts=0 and were genuine destroys - so an unknown number of those six historical "warm resets" were not, the control's true rate is unknown and likely below 43%, and the 0.57^7 power calculation resting on 43% claims more than it should.
