### RESMODESETNOTLIVEONRELOAD - our IDD reload ioctl returns before the mode set is live (P2, OPEN; agent-side workaround in place)

`SetVideoModeExact` publishes the computed mode set into the QubesIDD driver's registry key and makes the
driver reload it (`QiddReloadModes`, the IOCTL path). **The ioctl returns before Windows will accept the
mode.** MEASURED 2026-10-19, release 4.3.37 acceptance, win11-upgrade cell, agent pid 8132, one instance,
one clock:

```
003947.450  I QIDD ioctl-reload ok
003947.452  I M0BLINK reload-returned t=80656 sinceobtain=47 ms
003947.508  I RESWAIT 5120x1440 pre-flight skipped after 1 poll(s): the input desktop is the secure desktop
003947.508  I New resolution: 5120 x 1440
003947.997  E ChangeDisplaySettings failed: 0xffffffff          <- 58 ms after the reload returned
003947.997  W RESKEEP 5120x1440-unavailable keeping 0x0 reason=apply-failed-0xffffffff
003947.997  E NEVEREXIT SetVideoMode(5120x1440) failed (0xffffffff) - continuing at current resolution
003947.997  W NEVEREXIT adopted 1920x1080 as the current screen size
003949.585  I RESEXACT 5120x1440 replug=0                       <- the SAME mode, 1.6 s later, unaided
```

0xffffffff is DISP_CHANGE_FAILED. Nothing about the mode was wrong: it applied 1.6 s later with no
intervention. **The driver is ours**, so this is a defect on Track B, not a Windows quirk to live with: a
reload that has returned should mean the mode set is live, or the driver should expose a readiness signal
the agent can wait on.

WHY IT SURFACED NOW, and it is not a regression in the driver. The 2026-10-18 change stopped polling
CDS_TEST on the secure desktop, where that query can never see the mode, to remove a 12-second stall on the
sign-in screen. The discarded poll had been incidentally giving the reload time to land. Previous campaign:
0 pre-flight skips, 0 refusals. This one: 1 skip, 1 refusal, same instance.

**WORKAROUND (shipped 4.3.37):** `SetVideoModeInternal` takes a settling window and retries a refused apply
for up to `EXACT_MODE_APPLY_SETTLE_MS` (3 s, 250 ms steps) when nothing confirmed the mode was offered -
only for DISP_CHANGE_FAILED and DISP_CHANGE_BADMODE, the two a mode set that is still going live produces;
every other status stays final on the first attempt. A recovery is reported at WARNING as `RESSETTLE` with
the refusing status, and a window that expires keeps its ERROR. Jev: retry_apply 0.81, demote_when_recovered
0.91, gate_cannot_see_info 0.86 (which is why the recovery is WARNING rather than INFO - the gate grades
only W/E, so at INFO a guest that systematically needed retries could never fail acceptance).

**STILL OPEN:** the driver side. The workaround hides the symptom from the user, not the cause, and the
`RESSETTLE` warning is the standing measurement of how often it fires. It is accounted in
`mgmt/harness/error-ledger.txt` against THIS issue, not as normal behaviour.
