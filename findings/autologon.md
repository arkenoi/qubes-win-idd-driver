- Autologon is ENFORCED policy, not a convenience (owner: "this is the way we deal with lockouts"). Upstream QWT has no logon filter and defaults to a windowed desktop; our Mode-1 suppression makes an unarmed guest invisible, so the installer arms autologon on every image. Managed/domain/Windows-Hello images cannot be armed this way — deferred, task #31. [verified 2026-08-28]
- Arming mechanism PROVEN with a negative control that fired, and upheld by the evidence audit: `guest/set-autologon.ps1` validates credentials with LogonUser BEFORE writing anything (wrong password → `reason=bad-credentials`, AutoAdminLogon left 0), stores the password ONLY as the LSA secret `DefaultPassword` (no plaintext registry value; plaintext removed if present); a deliberately poisoned secret produced NO session, proving Winlogon reads the value we write. `guest/ensure-autologon.ps1` recognises the LSA secret (it used to report an armed guest as broken). Boot-time re-assert = SYSTEM scheduled task `QubesAutologonGuard` (BootTrigger PT30S, HighestAvailable). [verified 2026-08-29]
- TRAP — plaintext beats LSA: Windows PREFERS a plaintext registry `DefaultPassword` over the LSA secret. A testbed once carried a boot task `QwtAutologonRearm` (`C:\Windows\qwt-rearm-autologon.cmd`, hardcoded testbed creds, present in NO repo) rewriting the plaintext value every boot; while any such writer runs, no measurement of the LSA path means anything. Assert the plaintext value absent before any autologon measurement — set-autologon.ps1 now prints the registry state before deciding. [verified 2026-08-28]
- `AutoLogonCount` mechanism: while that registry value is present, Windows CONSUMES `DefaultPassword` (deletes it after one use), so autologon dies on the next reboot and the guest parks at sign-in. Answer files no longer write `<LogonCount>`; the LSA secret is not consumed this way; `AutoLogonCount` PRESENT on a guest = password being eaten toward a lockout (protocol SG6 checks it is ABSENT). Autologon acceptance always includes a reboot with the session REQUIRED back. [verified 2026-08-28]
- Session-presence instrument: `Win32_ComputerSystem.UserName` (empty until someone is logged on) — NEVER qrexec. On this testbed `qubes.VMShell` runs as NT AUTHORITY\SYSTEM with no session, so a guest parked at the sign-in screen answers every qrexec probe; any bootwait/alive-based "session restored" check measures nothing. [verified 2026-08-28]
