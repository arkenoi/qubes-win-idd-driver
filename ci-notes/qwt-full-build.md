# qwt-full — building the real QWT installer from source with our agent

Status: implementing (2026-08-01). Executes PLAN-full-source-build.md steps 1–3.
Inventory below was established from cloned upstream sources (paths under `upstream/ro/`),
by a fan-out inventory pass; every claim carries its evidence file.

## 1. How upstream actually builds QWT 4.2.2 (plan step 1)

- **There is no `qubes-windows-tools` meta-repo** (404). QWT is built by **qubes-builderv2**;
  the installer sources are **`QubesOS/qubes-installer-qubes-os-windows-tools`**, tag
  `v4.2.2-1` = `14c189e44fea99c0b42b029e96f172c7eecec5e0`.
- builderv2 flow: fetch each Windows component repo (signed-tag verified) per
  `example-configs/windows-tools.yml` → build each component's `.qubesbuilder`
  `vm.windows.build` .sln inside a **Windows dispvm** with the **EWDK ISO** attached
  (`qubesbuilder/plugins/build_windows/`, `executors/windows.py`, `scripts/build-sln.ps1`)
  → stage artifacts into a local repository as `<component>/{bin,inc,lib}` + `sign.crt`,
  exported as `QUBES_REPO`/`QUBES_INCLUDES`/`QUBES_LIBS` → installer builds last.
- Components: vmm-xen-windows-pvdrivers (KMDF, xenbits submodules xenbus e76d03e3 /
  xeniface 9cd9a604 / xennet ad7717f6 / xenvbd 054c2e53 / xenvif 9fd1afe4), core-vchan-xen,
  windows-utils, core-qubesdb, core-agent-windows, gui-common (headers only),
  **gui-agent-windows (shipped 4.2.2 = aeb7bf71)**, installer.
- **gui-agent is NOT a submodule anywhere** — an independent sibling component. The MSI
  takes exactly `$(env.QUBES_REPO)\gui-agent-windows\bin\{gui-agent.exe,gui-watchdog.exe}`
  (+ `sign.crt` when TEST_SIGN) — `vs2022/installer/GuiComponents.wxs`. dump-windows.exe
  is built upstream but not shipped.
- MSI/bundle: WiX **v4.0.5** SDK-style projects, nupkgs sha256-pinned, restored from a
  local `.distfiles` feed (`vs2022/nuget.config`). No harvesting — every file explicitly
  listed as `$(env.QUBES_REPO)\<comp>\bin\<file>` (all flat, 72 refs). `version.wxi`
  generated by an inline CodeTask reading `..\..\version` **relative to process CWD**.
  Bundle chains vc_redist (from `$(env.EWDK_PATH)`) + MSI; PostBuild renames to
  `qubes-windows-tools-<ver>.exe` and invokes `$(QB_SCRIPTS)\local\postbuild.ps1`
  (no-op unless QB_LOCAL=1, but the path must resolve).
- Signing: every bin artifact (.exe/.dll/.sys/.cat) Authenticode-signed with a vault-generated
  self-signed **CN="Qubes Windows Tools"** cert; public cert per component embedded in the
  MSI (Binary SigningCert*) and installed to LocalMachine\Root (never TrustedPublisher —
  hence install-helper.exe's ApproveTestSign prompt-clicker). MSI itself not signed;
  TEST_SIGN adds a TESTSIGNING launch condition.
- Feature map (from the .wxs): PvDriversCore = xenbus+xeniface (+certs);
  Core = qubesdb/qrexec/network-setup/RPC set + shared DLLs; Gui = gui-agent+watchdog+
  QubesGuiWatchdog svc; PvDriversNetwork = **xenvif+xennet only, DifX-staged**;
  PvDriversDisk = xenvbd/xendisk/xencrsh; MoveUsers; Autologon.

### PV network non-binding — root cause is NOT packaging
Our ADDLOCAL always included PvDriversNetwork and it staged fine. xenvif binds only when
XENBUS enumerates `XENBUS\VEN_XP0001&DEV_VIF` — which exists only with a netvm attached;
the emulated-NIC unplug is a **two-boot dance**: first PV start arms `Services\XEN\Unplug`
`NICS` and demands reboot (xenvif `pdo.c` PdoStartDevice → STATUS_PNP_REBOOT_REQUIRED);
next boot xen.sys consumes the value and unplugs — and the unplug is VETOED until a VIF has
been enumerated at least once (`xen/unplug.c` UnplugCheckEnumKey). Ranked causes for the
observed hang-on-netvm: (1) missing reboots after first netvm attach; (2) TrustedPublisher
prompt on the deferred PnP install (our install-qwt.cmd already pre-trusts, so less likely
for us). Guest discriminator: `setupapi.dev.log`, `Enum\XENBUS`, `Services\XEN\Unplug`,
driver store `oemNN.inf`. **Remedy expected: attach netvm, reboot twice.**

## 2. Integration decision (plan step 2)

Neither plan option applies as written:
- (a) "submodule override" — no submodule exists; the real equivalent is a builderv2
  per-component `url/branch` override, which needs the full builderv2 Windows infra
  (win-build worker qube + EWDK ISO + vault-sign qube) that this environment doesn't have.
- (b) post-build cab substitution — unnecessary, since the MSI can be rebuilt from its real
  sources cheaply.

**Chosen: (c) rebuild `installer.msi` (+ bundle) from the genuine upstream WiX v4 sources
(pinned v4.2.2-1) in GitHub CI**, staging `QUBES_REPO` with:
- **our** CI-built, throwaway-cert-signed `gui-agent.exe`/`gui-watchdog.exe` (+ our cert as
  `gui-agent-windows\sign.crt`) — the guest already trusts that cert (Root+TrustedPublisher,
  firstboot-setup.ps1);
- **everything else bit-identical** from the shipped 4.2.2 MSI (`vendor/qwt-4.2.2/`,
  provenance in its README), ITL Authenticode signatures intact, ITL certs vendored as the
  other components' `sign.crt`.

EWDK-in-CI is infeasible (~15 GB vs runner disk/cache); pvdrivers-from-source via the proven
83 s choco-WDK recipe is a possible later lane, but buys nothing today (we change no driver).
Rebuilding the other user-mode components from source likewise adds attribution surface where
we changed nothing. This decision delivers the plan's actual goals: the *install* is ours and
manifest-recorded, no overlay, PV drivers exactly the verified upstream bits.

## 3. Implementation

- `.github/workflows/qwt-full.yml` — single windows-2022 job: proven agent-build steps from
  build.yml (dep pins, xencontrol.lib synthesis, staging) → sign our exes + export sign.crt →
  verify + `msiexec /a` the vendored MSI → `packaging/stage-qwt-repo.ps1` (parses the .wxs
  QUBES_REPO refs, satisfies each from our bins/admin image, fails on missing/ambiguous) →
  populate `.distfiles` (nupkgs sha256-verified against the repo's pins) → fake EWDK tree
  with the runner's vc_redist → `msbuild -restore installer.sln` with TEST_SIGN=1,
  CWD=vs2022\installer (CodeTask relative paths) → artifact `qwt-full-package`
  (installer.msi, bundle, our exes, MANIFEST.json with all provenance shas).
- Requires repo secrets SIGNING_PFX_B64/SIGNING_PFX_PASS + var SIGNING_ENABLED=true
  (workflow fails early otherwise).

### Expected friction (budgeted)
- CreateVersionWxi uses `CodeTaskFactory` + `Microsoft.Build.Tasks.v12.0.dll` — if the
  runner's MSBuild lacks the facade, patch the wixproj in-workflow to RoslynCodeTaskFactory.
- WiX SDK resolution from the local feed; DifxApp wixext x64 warnings; bundle PostBuild
  `$(SolutionDir)` semantics (why we build the .sln, not the .wixproj, and `-m:1`).
