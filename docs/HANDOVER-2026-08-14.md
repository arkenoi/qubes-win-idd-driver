## Two testing traps that cost hours today

* **Test through the PACKAGED INSTALLER, not a piecemeal deploy.** Update testing here deployed
  `install-updater-agent.ps1` alone, which is why OneDrive came back and the desktop tuning was
  absent - a configuration no user ever has.
* **A pristine rebuild silently reverts state you "fixed".** The certificate-trust-list cache did

  always passes. Both earlier "successes" were warm-cache and would have shipped broken.

## KNOWN LEAK, fix already specified - cached .msu never reclaimed after a staged install

`qubes-windows-update.ps1` deletes a package's cached `.msu` only when the pass did NOT stage
anything (`if (-not $staged)`), so:

    rc=0    applied immediately -> deleted, space reclaimed
    rc=3010 staged              -> KEPT, so a failed apply does not cost a 4.8 GB re-fetch

That second rule is deliberate and it works - the 2026-08-14 second pass reused the cached file
("already complete ... server refused resume with 416") instead of re-downloading. But the condition
only asks "was something staged in THIS pass", never "did the staged thing eventually land". A
package staged and then successfully applied at the next boot is **never cleaned up**: 4.8 GB per
cumulative sits in `C:\ProgramData\Qubes\wu` on a TEMPLATE, indefinitely.

FIX (small, and it belongs at the TOP of the per-KB loop rather than the bottom): before acting on a
KB, check whether it is now present in CBS with `state=112` and, if so, delete its cached files.
That reuses the same signal the acceptance criterion already uses rather than inventing one, and it
self-heals across passes - including for packages staged by a pass that later crashed.
