TWO CONSTRAINTS THAT MUST BE STATED WHEREVER THIS IS DOCUMENTED:

1. **One reboot-requiring package per pass.** CBS discards a second staged package - measured twice,
   with RebootPending confirmed and TiWorker idle, so it is not a shutdown race. dom0 must therefore
   drive a SECOND pass to pick up the deferred package. `QUBES_UPDATES_ALLOW_MULTISTAGE=1` re-tests
   this on other builds; it stays OFF by default.
2. **The domain teardown can hang** - see below. A user who does not know to kill the qube is
   stranded, so this needs either a fix or a documented recovery step before it ships to anyone.

## NEW, UNDIAGNOSED: domain teardown hangs after the update reboot

At the end of the successful pass the guest sat on "Restarting" burning exactly ONE core for ~20
minutes. That CPU shape is consistent with the offline commit (poqexec is single-threaded; the
multi-core phase is TiWorker staging, already finished at 842 CPU-s) - but the decisive signal was
in dom0: `qvm-ls` showed **Transient**, not Running, for 8+ minutes. Windows had finished and issued
its restart; the DOMAIN teardown hung (`on_reboot=destroy`).

Killing it was safe and correct - the subsequent boot showed 26100.9168 with clean CBS, i.e. an
already-committed Windows was destroyed, not a live transaction.

DIAGNOSTIC RULE for a stuck "Restarting", check dom0 state FIRST:
    Running    -> still working, DO NOT TOUCH (killing mid-commit is how CBS gets corrupted)
    Transient  -> Windows is done and the domain will not die; kill is safe

WHY it hangs is unknown and was not investigated. It cost ~20 minutes here.

## KNOWN LEAK, fix already specified - cached .msu never reclaimed after a staged install

`qubes-windows-update.ps1` deletes a package's cached `.msu` only when the pass did NOT stage
anything (`if (-not $staged)`), so:

    rc=0    applied immediately -> deleted, space reclaimed
    rc=3010 staged              -> KEPT, so a failed apply does not cost a 4.8 GB re-fetch

That second rule is deliberate and it works - the 2026-08-14 second pass reused the cached file
("already complete ... server refused resume with 416") instead of re-downloading. But the condition
only asks "was something staged in THIS pass", never "did the staged thing eventually land". A
package staged and then successfully applied at the next boot is **never cleaned up**: 4.8 GB per
cumulative sits in `C:\ProgramData\Qubes\wu` on a TEMPLATE, indefinitely.

FIX (small, and it belongs at the TOP of the per-KB loop rather than the bottom): before acting on a
KB, check whether it is now present in CBS with `state=112` and, if so, delete its cached files.
That reuses the same signal the acceptance criterion already uses rather than inventing one, and it
self-heals across passes - including for packages staged by a pass that later crashed.
