# GWeck v4.3.1 field report — investigation synthesis (workflow wf_f97c6c71, 52 agents, 2026-08-11)

## S1a - Start menu renders as garbled graphics on Win11 25H2 (IDD active)

**Cause:** PROVEN (static) + LIKELY (rendering outcome): On 25H2 the Start menu is no longer a Windows.UI.Core.CoreWindow but a full-screen (0,0,1920,1080) unowned untitled POPUP|TOPMOST|TOOLWIN window, class Wnd_StartFeed (StartMenuExperienceHost) - GWeck's winenum.log line 5, /home/user/qubes-win-idd-driver/instrumentation/gweck-post44/winenum.log. Because its size equals the host screen, IsPopup's too-large check (agent/gui-agent/main.c:826-831, '>=' fires on equality) demotes it from popup to NORMAL window; it then passes every ShouldAcceptWindow rule (ex=0x00010088: no TRANSPARENT/LAYERED/NOREDIRECTIONBITMAP, unowned, uncloaked when open). The agent announces an untitled full-screen window and, since the demotion cleared override-redirect, PwAttachWindow attaches it PrintWindow-fed (main.c:1311-1314, perwindow.c:213-246) - PrintWindow of a XAML/DirectComposition host is the code-documented unreliable capture path, the plausible garble mechanism. Additionally ALL of the agent's Start special-casing is dead code on 25H2: g_StartWindow = FindWindow(L"Windows.UI.Core.CoreWindow", L"Start") (agent/gui-agent/util.c:328) returns NULL because no such top-level window exists in the 80-line dump, so main.c:792-801, main.c:2027-2031 and main.c:1651 never execute. Secondary artifact source: ForegroundStaging windows (ex=0x08200088, NOREDIRECTIONBITMAP without TRANSPARENT) escape the shell-overlay rule (main.c:2061-2063 requires all three bits) and, if caught visible during the Win-key transition, would map as slice-fed phantom windows.

**Fix:** In agent/gui-agent/main.c ShouldAcceptWindow / IsPopup: (1) do not blind-accept a full-screen unowned untitled TOOLWINDOW popup as a normal window - either reject Wnd_StartFeed-shaped shell surfaces (toolwindow + topmost + unowned + untitled + screen-sized) or keep them override-redirect and slice-fed instead of PrintWindow-fed; (2) extend the 2A-chrome predicate so NOREDIRECTIONBITMAP toolwindows without TRANSPARENT (ForegroundStaging) are filtered; (3) port the Start/Search detection to the 25H2 classes (Wnd_StartFeed) or delete the dead g_StartWindow machinery. Toast acceptance test from CLAUDE.md 2A-chrome 3c must gate any new filter.

**Ours/user:** Ours (agent window-acceptance code, pre-existing; newly exercised because 4.3.1 made the IDD active by default on a 25H2 guest - proven that agent+driver code is identical between the releases GWeck ran, so this is environmental exposure, not a code regression)

## S1b - dom0 gui-daemon dialog 'invalid or suspicious GUI request' (Ignore/Terminate) when Start menu opens - the highest-severity item

**Cause:** PROVEN by elimination which check fires; source of bad value UNEXPLAINED - needs repro/logs. The dialog is produced solely by ask_whether_verify_failed() (upstream/ro/qubes-gui-daemon/gui-daemon/xside.c:154-228), reachable only via the VERIFY macro (xside.c:88). Of the 5 active VERIFY sites, this agent build can trip exactly ONE: MSG_CREATE with width or height >= 2^31, i.e. negative-as-int (xside.c:2937). Proven exclusions: agent never sends MSG_CURSOR (zero grep hits); MSG_WINDOW_FLAGS masks are constant and disjoint at all 4 call sites; MSG_CONFIGURE zero-size is guarded agent-side (send.c:600) and negative-as-huge values are clamped by the daemon BEFORE its VERIFY (xside.c:2093-2099). SendWindowCreate (agent/gui-agent/send.c:287, width/height at :329-330) ships raw uint32 rect math with NO guard, and a negative-as-DWORD width evades every agent-side size gate (unsigned compares main.c:2043/2046; IsPopup demotion main.c:826 even guarantees announcement as a normal window). WHAT PRODUCES the negative dimension on 25H2 is NOT established: the proposed g_StartWindow rect-inversion mechanism (main.c:792-801) was REFUTED - g_StartWindow is NULL on 25H2 per the winenum dump, so that code cannot run. Unverified candidate: GetRealWindowRect's unchecked EnumDisplaySettings/DPI-scale LONG-cast math (main.c:750-760) on the newly-default IDD monitor. Consequence chain (proven): while the dialog is up the daemon blocks in waitpid (xside.c:205), vchan backpressure freezes the desktop; if the user clicks Ignore, handle_create returns before list_insert (xside.c:2952), so the next message for that hwnd hits 'msg without CREATE' and exit(1)s the daemon (xside.c:3952-3956) - the qube loses its GUI either way.

**Fix:** Two-part. (1) STRUCTURAL, ship regardless of root cause: add an (int)width/height > 0 guard (with logging) in SendWindowCreate (agent/gui-agent/send.c:325-347) mirroring the existing SendWindowConfigure guard at send.c:600, plus rect validation (right>left, bottom>top, fall back to the unclipped rect) after any fix-up in GetRealWindowRect (agent/gui-agent/main.c:784-801). This makes the scary dom0 dialog unreachable from geometry bugs, forever. (2) DIAGNOSTIC: instrument GetRealWindowRect's EnumDisplaySettings/scale path (main.c:750-760) to log inputs when the computed rect is inverted, and get the guid log from GWeck - the dialog's log line names the exact failed VERIFY expression, converting elimination into direct proof.

**Ours/user:** Ours (agent sends the protocol-violating MSG_CREATE; the daemon's dialog is working as designed). The daemon-side Ignore-path issues (mid-parse return leading to exit(1), and a leaked vm_window) are upstream gui-daemon defects potentially reportable under the CLAUDE.md exception - user must approve any text first.

## S2 - mouse pointer ~1cm vertically below where Windows thinks it is (new on 4.3.1 = IDD-active)

**Cause:** LIKELY (two candidates, one log pull discriminates; mechanism-level facts proven, trigger on GWeck's box inferred). Injection normalizes dom0 coords against the agent's BELIEVED screen size: HandleMotion dy = y*65535/g_ScreenHeight with MOUSEEVENTF_ABSOLUTE, no VIRTUALDESK (agent/gui-agent/vchan-handlers.c:491-494), so Windows maps onto the ACTUAL primary monitor; any believed-vs-actual height divergence gives a proportional vertical-only error (clicks inherit it - HandleButton's dx/dy are ignored by Windows, no MOVE|ABSOLUTE flags). CANDIDATE 1 (leading, IDD-only, exact vertical-only signature): the A4CLAMP boot clamp requests a height-only-smaller mode (1920x~1020 from the dom0 work-area, vchan-handlers.c:177-210); if 25H2 half-applies the dynamic IddCx mode (documented for 24H2 in FINDINGS.md ~3072, VirtualDrivers#471; SDC_FORCE_MODE_ENUMERATION mitigation NOT implemented in the agent), the readback-verify only LOGS 'RESAPPLIED-MISMATCH' and then stores the REQUESTED size (resolution.c:1167-1179, 1207-1208) - agent believes 1920x1020, desktop is 1920x1080 (winenum confirms 1080), error = +25..47px downscreen = ~1cm, horizontal exact. Unreachable on the 4.3.0/BDA path (fixed mode list) - matching the version correlation. CANDIDATE 2 (measured precedent in this repo): a second attached display beside the IDD caused exactly 'CM-scale input-coordinate skew' + double cursor (FINDINGS.md 2026-08-05); EnsureQubesIddSolo (resolution.c:137-270) runs ONCE at startup, non-fatal, never re-asserted, and 25H2's OS-side topology behavior is untested. RULED OUT (proven): EDID/DPI rescale (v4.3.1 ships physical-size-undefined EDID, commit 6f1e2f4 in the tag; GWeck's DPI-unaware winenum reads exactly 1920x1080 = 100% scaling) and stride/pitch (would shear horizontally).

**Fix:** In agent/gui-agent/resolution.c: on RESAPPLIED-MISMATCH adopt the APPLIED (read-back) size into g_ScreenWidth/g_ScreenHeight instead of the requested size (1207-1208, 1289-1290), and implement the SDC_FORCE_MODE_ENUMERATION poke after publishing a new mode so the desktop actually follows. For candidate 2: re-assert IDD solo topology on WM_DISPLAYCHANGE (agent/gui-agent/workarea.c:381 currently re-asserts only the work area) instead of once at startup (main.c:4934).

**Ours/user:** Ours (agent stores unverified geometry; missing mode-enumeration poke; one-shot solo assertion). Environmental trigger is the 4.3.1 IDD-default flip, not a code regression.
