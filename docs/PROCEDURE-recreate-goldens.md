# PROCEDURE — recreate goldens (when none exist)

Load this only when the goldens are missing or their seals fail `mgmt/golden.sh verify`. The
current set, which is what `mgmt/goldens/` holds a seal record for:

| golden | what it is |
|---|---|
| `win10-base` | pristine base, `Win10_22H2_EnglishInternational_x64v1.iso`, PRIMER=1, no QWT |
| `win11r-base` | pristine base, `Win11_26300_English_x64.iso`, PRIMER=1, no QWT |
| `win11r-qwt` | retail Win11 QWT golden, built from the clock-corrected `win11r-base` |
| `win11de-qwt` | German 25H2 QWT golden |

This list named `win11-base`, `win11-qwt` and `win10-qwt` until 2026-10-27. All three are gone —
`win11-base`'s seal was deleted in `d5781e55` because the image was gone, `win11-qwt` in `b1fb0cea`
when the eval-based golden was replaced by retail `win11r-qwt`, and `win10-qwt` never had a seal
record at all. Read literally, the old list made an intact pool fail this file's own trigger and
sent the heavy recreate procedure at goldens that are fine. CLAUDE.md corrected the same stale list
in itself on 2026-10-21 and this file was missed.

**There is no hand path.** `mgmt/harness/golden_recreate.sh` is the only way a golden is recreated
or resealed (plan step 9, `docs/PLAN-harness-refactor.md`: "No other log walks, clock sets, or
golden prose procedures"). This file is the authority for *why* — the preconditions, the evidence
rules and the gate exception the script enforces. A prose procedure cannot refuse to run; the
script can, and does.

## Evidence rules (binding)
- Never claim a snapshot, revision, or pre-damage state exists unless you have just run the command that shows it and pasted the output.
- `qvm-volume info <vm>:root` (and private) is the only source for revision lists. A claim without that output is false.
- Every `mgmt/golden.sh verify` must show its exit code and the VERIFIED or REFUSE line. No summary substitutes for the output.
- During any install or boot longer than 5 minutes, take a screenshot with `tools/qtest shot` at least every 15 minutes and record the path. Zero screenshots on a long run is a failure of the procedure.
- Answer files / unattend files must be the ones already committed in the repo or generated by the existing harness scripts. Do not hand-write a new one and give it a long budget.

## Preconditions
- No Windows guests running.
- Vendor install media available to the existing reprovision path (`mgmt/reprovision-usb.sh` or the documented equivalent that produces a Halted pristine base).
- For a QWT golden: an N-1 release setup tree (install.cmd + MANIFEST.json at root) available on disk. If missing, obtain it from CI artifacts of the previous release; do not build a new one for this purpose.

## The command

One command, once per golden. There is no step 1 to do by hand.

```
mgmt/harness/golden_recreate.sh --golden <name> --base <pristine-base> \
    [--setup <N-1-setup-tree>] [--reprovision <iso-loop> <stick-loop>]
```

- With `--setup`, the QWT golden is built from the base via `seal-qwt-golden.sh`, then sealed and verified.
- Without `--setup`, it reseals `<base>` itself, and `<golden>` must equal `<base>`.
- With `--reprovision`, the pristine base is **built here** via `mgmt/reprovision-usb.sh` with `PRISTINE=1` when it is absent or not Halted — after the golden-verify gate, so an intact golden never costs a reprovision. That script asserts sole guest, tags the vm `win-idd-testbed` and leaves it Halted.
- It refuses, rather than proceeding, when: no Jev receipt carries `recreate_goldens`; the base is absent or not Halted and no `--reprovision` was given; the golden already verifies against its seal; or a reseal would abandon revisions already gone without `GOLDEN_RESEAL_REASON`.
- It never starts a golden. `tools/hooks/golden-boot-gate.sh` refuses a start regardless.
- Exit: 0 sealed and VERIFIED (or already was); 1 a precondition refused; 2 usage; 3 the build, the reprovision or the verify failed.

Do not run `mgmt/golden.sh seal`, `mgmt/golden.sh verify`, `seal-qwt-golden.sh` or
`reprovision-usb.sh` by hand for this purpose. The script drives them in order with the refusals
attached; driving them separately is the second recreate path step 9 removes.

Only after the golden verifies may short-cycle work resume.

**What is deliberately NOT scripted:** obtaining the vendor ISO and the N-1 release setup tree, and
putting them on loop devices. That is the one non-deterministic step, and it is excluded on
purpose — see Preconditions. Everything downstream of it is the command above.

## Gate exception
When no golden exists, there is no short-cycle alternative. A Jev call whose state contains the
marker `recreate_goldens` and quotes the command above (or the path to this file) satisfies
`tools/hooks/committed-procedure-gate.sh` for the heavy steps in this sequence
(`reprovision-usb.sh`, `prime-run.sh`, `seal-qwt-golden`). `golden_recreate.sh` checks for that
receipt itself and refuses without it.

Any other heavy command still requires the normal "exact command + rejected short-cycle" justification.

## After success
Record the N-1 version that was sealed (already written by `seal-qwt-golden.sh` into
`mgmt/fixtures/<os>-qwt.json`). Do not start the goldens. Clone only.

## What `protocol/steps/golden.json` is, and why it is not a second copy of this

`protocol/steps/golden.json`, scheduled by `protocol/run.py`, drives `reprovision-usb.sh`,
`golden.sh seal` and `golden.sh verify` for the R3 / ST0 / ST2G steps of an acceptance campaign.
It *looks* like the sequence above. It is not one — it is **nine independently graded steps whose
contracts contradict each other**:

| step | contract |
|---|---|
| `st0-r3` | expects **exit 3** + `"NEEDS VISUAL CONFIRMATION - READ .../latest.png"` — on the pristine QWT-free path a non-zero exit with a pixel instruction *is* success, because that image never gets qrexec |
| `st2g-r3` | expects **exit 0** + `"qrexec alive after <n>s"` — the opposite contract, same file |
| `st0-freshname`, `st2g-freshname` | run `verify` on the **target** and expect **exit 2 `UNSEALED`**, asserting the name is *not* sealed so R3 cannot destroy a sealed golden — the inverse of `golden_recreate.sh`'s "already verifies → nothing to do" |
| all nine | carry their own `HALT_CAMPAIGN` verdict and operator diagnostic that `run.py` grades |

Only the two R3 steps name a guest, so only they take `run.py`'s vmlock; folding the seal and
verify steps into one invocation would put them inside a lock that today does not cover them.

Shown those contracts verbatim, Jev answered that a single invocation **cannot** carry them
(1.00) and that these steps are a **different operation** from a recreate (0.91): a campaign
building *fresh-named* goldens under per-step grading, not the recovery of a lost or drifted one.
An earlier call given only a prose summary said the opposite and was revised at 0.88 once the
contracts were shown.

**The division: `protocol/` builds goldens inside an acceptance campaign; `golden_recreate.sh`
recreates one that is lost or drifted, outside any campaign.** Do not collapse them — the collapse
destroys real assertions, and a step invoking this script from a guest-bearing step would meet its
own parent's live vmlock (`run.py:437-443` uses the same `qwt-vmlock-<g>` file).
