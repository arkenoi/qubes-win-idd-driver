# Toast fix — judged patch plan (workflow wf_686724f7, 8 agents, 2026-08-11)

## Verdict

MERGE, base = Design B (correctness-first), with two elements salvaged from Design A and three of A's edits rejected as wrong. Verified against source during judging: (1) Design A's clickability rationale is factually false at runtime — HandleButton's dx/dy are dead code because its dwFlags never includes MOUSEEVENTF_ABSOLUTE|MOUSEEVENTF_MOVE (vchan-handlers.c:403-435), so clicks land at the cursor position HandleMotion already set from tracked data->X/Y; B's 'inert but truthful' framing is correct. (2) A's edit 4 (RemoveWindow+AddWindow on IsPopup flip) duplicates existing machinery: UpdateWindowData already detects popup-state flips and calls ToggleMap (main.c:2381-2431), which sends UNMAP+MAP+PwRemapWindow (main.c:841-863); a fresh MSG_MAP re-latches override_redirect daemon-side (xside.c:3539), so no recreate is needed — only a trigger. (3) A's edit 5 (4x4 AddWindow floor for popups) would REGRESS the deliberate sub-floor-popup silent drop protecting against the Win11 Alt-keytip 12-bordered-badges defect (main.c:1282-1295 comment), and is unnecessary since the cropped card (364x90) clears the ~136x39 floor. (4) B's one real gap, which A found: a transient toast rect in the 90-100%-of-work-area band passes the agent's full-screen IsPopup guard (main.c:826) but gets OR-stripped by the daemon (xside.c:1978); with B alone (if UIA transiently yields zero insets) the agent's classification never flips, ToggleMap never fires, and the window is WM-managed mid-screen forever — A's IsPopup threshold alignment is the minimal correct trigger for the EXISTING ToggleMap path. (5) B's HandleConfigure suppress-and-resync (modeled on the IsZoomed branch, vchan-handlers.c:534-552) is safer than A's live-delta SetWindowPos, which would write dom0 geometry into a shell-owned HWND and still lets the else-branch (vchan-handlers.c:578+) stomp cropped tracked fields. (6) A's hardcoded insets as primary crop source fail dangerously (silent overcrop clipping the 40x40 action buttons on other builds/DPI/themes) versus B's UIA-with-zero-inset-fallback which fails soft to today's behavior; A's registry override survives as a manual escape hatch only. Neither design's unreproduced HUGE/mid-screen mechanism is treated as proven; the merged plan heals it via two independent, individually-justified layers (crop keeps the rect small; threshold alignment + ToggleMap recovers OR if a huge announce ever happens).

## Final plan

AGENT-ONLY toast fix (fork; zero GUI-protocol changes, zero daemon changes, no notification forwarding). Root causes, all recon-verified: HUGE = the toast HWND's GetWindowRect equals DWMWA_EXTENDED_FRAME_BOUNDS (delta ZERO, guest-probe), so the 16/30/16/13px margin is XAML shadow INSIDE the 396x133 window; the slice-fed path (perwindow.c:223 -> PwSliceCopyAndDamage main.c:2857-2898) ships composited-desktop pixels for the whole reported rect. MID-SCREEN = an oversized rect loses override_redirect either agent-side (IsPopup main.c:826-831, >= full screen) or daemon-side (validate_override_redirect xside.c:1942-2003, >90% work area, xside.h:58); once non-OR, mkwindow sends only PSize hints (xside.c:366) so the dom0 WM places the window. UNCLICKABLE = consequence of the OR-stripped variant (geometry desync + dom0-WM configure echoes fighting the shell via SetWindowPos), NOT missing keyboard focus — Linux parity: popups are pointer-only, MSG_BUTTON is delivered position-based regardless of focus (xside.c:1674), and the banner lacks WS_EX_NOACTIVATE so a real injected click activates it in-guest.

MECHANISM: (1) Crop the announced/captured rect to the visible card. New WINDOW_DATA fields CropLeft/Top/Right/Bottom; a new toastcrop module classifies the toast HWND (narrow signature from the guest probe: class Windows.UI.Core.CoreWindow, WS_POPUP, ex TOPMOST|NOREDIRECTIONBITMAP, NOT TRANSPARENT, NOT TOOLWINDOW, unowned, uncloaked, PID image ShellExperienceHost.exe, size ceiling to exclude Action Center) and measures the card via UIA (FindFirst descendant ClassName in {FlexibleToastView, ToastView} -> CurrentBoundingRectangle), cached per (HWND, rawW, rawH) with bounded retries; any failure = zero insets = today's uncropped-but-working behavior (toasts are REQUIRED-kept; the module only ever shrinks geometry of already-accepted windows, never feeds rejection). Registry override values allow forcing fixed insets or disabling the crop (escape hatch from A). The crop is applied at BOTH writers of the canonical rect: GetWindowData (before the WS_MAXIMIZE clamp at main.c:977 and before IsOverrideRedirect=IsPopup at main.c:1010, so OR is evaluated on the cropped size) and the frame-loop pre-damage refresh (main.c:3872-3888, cached insets only — no UIA), so every consumer (MSG_CREATE send.c:319-330, MSG_CONFIGURE main.c:1377, slice grant+copy perwindow.c:270/328 + main.c:2867-2888, damage conversion main.c:3947-3951, occlusion) is consistent by construction and the PwResizeWindow rebuild (main.c:2439-2455) fires exactly once when insets first apply — the WS_MAXIMIZE-clamp precedent (main.c:977-1008). A floor guard in toastcrop rejects insets that would shrink the rect below the AddWindow drop threshold (main.c:1288-1295), so the deliberate sub-floor-popup drop is left untouched. (2) Keep/recover override_redirect: align IsPopup's oversize demotion with dom0's 90%-of-work-area rule (xside.h:58) so any daemon-side OR strip is mirrored agent-side; the EXISTING popup-state-flip machinery (UpdateWindowData main.c:2381-2431 -> ToggleMap main.c:841-863: UNMAP+MAP) then automatically restores OR when the toast settles at cropped/real size, because the daemon re-validates and re-latches override_redirect at each MSG_MAP (xside.c:3539). No recreate machinery. (3) Guest-authoritative placement: with OR intact the daemon honors guest (x,y) verbatim (xside.c:372) and Windows already places the toast flush bottom-right (probe: right edge 5120, bottom at taskbar top 1392) — bottom-right placement falls out of the crop; the agent adds NO positioning logic (Linux parity, and memory rule never-resize-to-viewport). (4) Clickability: suppress dom0-initiated SetWindowPos for cropped windows in HandleConfigure (ignore + ACK-resync, the in-tree IsZoomed precedent) so dom0 coords in cropped space can never displace the shell-owned HWND; unify HandleButton's origin math on tracked data->X/Y like HandleMotion (runtime-inert today since dx/dy are ignored without MOUSEEVENTF_ABSOLUTE|MOVE — verified — but mandatory for coherence and future-proofing); add NO focus machinery (Linux popups never receive MSG_FOCUS and work pointer-only; the banner is not NOACTIVATE so the injected click activates it in-guest, giving keyboard-capable interactive toasts transitively).

OUT OF SCOPE, unchanged: the lingering PopupHost tooltip (separate ticket); MSG_FOCUS for OR windows; making HandleButton dx/dy live (behavior change for all clicks, own regression run); daemon-side code (upstream, read-only); any toast forwarding to dom0's notification daemon (spoofing surface, rejected upstream); daemon-side bordering (never weakened — the colorful frame will overlay ~2px of card edge, accepted cosmetic).

## Rejected ideas

- Design A edit 4 (RemoveWindow+AddWindow recreate on IsPopup flip): redundant — UpdateWindowData already handles popup-state flips via ToggleMap (main.c:2381-2431 -> 841-863, UNMAP+MAP+PwRemapWindow), verified in source; the daemon re-latches override_redirect at each MSG_MAP (xside.c:3539). A recreate would fight this machinery, lose daemon-side window state, and blink borderless apps crossing the threshold.
- Design A edit 5 (relax AddWindow's popup floor to 4x4): regression — the g_MinWindow* drop at main.c:1282-1295 is the deliberate fix for Win11 Alt-nav keytip badges ('not appearing beats appearing wrong'); relaxing it reintroduces the 12-bordered-badges defect. Unnecessary anyway: the cropped card (364x90) clears the ~136x39 floor; the toastcrop floor guard makes sub-floor results unreachable.
- Design A's hardcoded DPI-scaled insets (16,30,16,13) as PRIMARY crop source: measured on one build (26100) at one DPI; fails DANGEROUSLY (silent overcrop clipping the 40x40 action buttons) on other builds/themes/expanded toasts, versus UIA's safe zero-inset fallback. Retained only as a registry escape hatch (ToastCropL/T/R/B) plus ToastCropDisable.
- Design A's HandleConfigure live-delta transform (offset-corrected SetWindowPos): writes dom0-originated geometry into a shell-owned HWND (ShellExperienceHost layout corruption risk) for a path toasts exercise at most via a zero-nudge force_on_screen; the in-tree IsZoomed suppress+ACK-resync precedent is strictly safer.
- Design A's claim that the HandleButton origin change fixes clickability: factually wrong at runtime — dx/dy are ignored because dwFlags never includes MOUSEEVENTF_ABSOLUTE|MOUSEEVENTF_MOVE (verified, vchan-handlers.c:403-435). The edit is kept (from B) as an inert coherence fix with a corrected rationale.
- Making HandleButton dx/dy live by adding MOUSEEVENTF_ABSOLUTE|MOUSEEVENTF_MOVE: changes injection behavior for ALL clicks (drag/double-click semantics); separate work needing its own interleaved regression run.
- Any keyboard-focus machinery for OR toasts (MSG_FOCUS, SetForegroundWindow-on-MSG_BUTTON): Linux parity — popups never receive MSG_FOCUS and work pointer-only; the banner lacks WS_EX_NOACTIVATE so the injected click activates it natively in-guest.
- Agent-side toast repositioning to the viewport corner: guest-authoritative placement is the Linux-parity rule and the memory rule (never resize/reposition on dom0's behalf); Windows already places the toast flush bottom-right — placement falls out of the crop.
- Forwarding toasts to dom0's notification daemon: explicitly out of scope — spoofing surface, rejected upstream.
- Daemon-side changes (validate_override_redirect threshold, focus for OR windows, border weakening): upstream read-only tree, and weakening bordering is prohibited; the colorful frame overlaying ~2px of card edge is accepted cosmetic.
- Folding the lingering PopupHost tooltip (Xaml_WindowedPopupClass, WS_EX_NOACTIVATE) into this fix: separate guest-side visibility defect, tracked as its own ticket so this diff stays reviewable.
